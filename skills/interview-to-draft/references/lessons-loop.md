# Approved Lessons Loop

Use corrections to improve future runs without turning one-off preferences into permanent rules.

## Compare

When the user revises or rejects the draft, compare:

1. The generated draft
2. The user's final edit or explicit correction
3. Existing project and platform rules
4. Previously approved lessons, if available

Describe the observable change before inferring a rule.

## Classify

- **Run-specific:** Applies only to this topic, example, source, or format.
- **Format-specific:** Applies to a newsletter, LinkedIn post, proposal, or another defined output.
- **Project-wide:** Applies across repeated work in the current project.
- **Skill behavior:** The interview, evidence, drafting, or review procedure itself should change.

## Promotion test

Propose a lasting lesson only when at least one is true:

- The user explicitly says "always," "never," or equivalent.
- The same correction appears more than once.
- The correction changes factual integrity, approval boundaries, or a major quality standard.
- Forgetting it would predictably recreate the same failure.

Keep other feedback in the run record.

## Approval boundary

Write every candidate to `proposed-lessons.md` with its evidence and scope. Ask the user to approve, revise, or reject it.

Do not automatically edit a shared style guide, standards file, instruction file, memory store, or the Skill itself. After approval, write the lesson to the narrowest location that will reliably affect future work.
